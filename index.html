대표 사례 (프로젝트 종료 후 개인 작업)

화재 경보가 참조 오류로 저장되지 않을 수 있었습니다

  1. 무엇을 봤나

    프로젝트가 끝나고 ERD를 다시 그려 보니, 테이블 사이에 외래키가 하나도 없었습니다. 실제로 없는 이벤트 ID로 영상을 등록해도 API가 아무 문제 없이 받아 주고 있었습니다.

  2. 어떻게 정했나

    외래키를 모든 관계에 똑같이 걸지는 않았습니다. 대신 “이벤트가 지워지면 이 데이터는 어떻게 돼야 하지?”를 관계마다 따져 봤습니다. 이벤트가 없으면 의미가 없는 알림 발송 기록은 같이 지우고(CASCADE), 증거로 남아야 하는 영상은 연결만 끊었습니다(SET NULL).

  3. 일부러 비워 둔 곳

    경보가 가리키는 설비와 지도에는 외래키를 걸지 않았습니다. 로봇이 아직 등록되지 않은 설비 기준으로 경보를 보내면, 외래키 때문에 저장 자체가 실패하기 때문입니다. 화재 경보를 통째로 잃는 것보다는 참조가 조금 어긋나도 남아 있는 편이 낫다고 봤습니다.

  4. 결과

    스키마를 Flyway로 옮기고, 테스트 220건이 GitHub Actions에서 실제 MySQL 8 위로 자동 실행되게 했습니다. 처음에 봤던 영상 등록 문제가 이 테스트에서 걸려, 지금은 400으로 거절합니다.

  5. 아직 남은 일

    알림 워커가 외부 HTTP 호출을 트랜잭션 안에서 하고 있어서, 알림을 보낸 뒤 커밋이 실패하면 같은 알림이 두 번 나갈 수 있습니다. 외부 호출을 트랜잭션 밖으로 빼는 것이 다음 할 일입니다.

배포 서버 방화벽에 로봇 연결이 막혔습니다

로봇 통신을 TCP 9000번 포트로 만들었는데, 막상 배포해 보니 서버가 이 포트를 막고 있었습니다. 그래서 Nginx를 거쳐 443번 포트로 들어오는 WSS로 바꿨습니다. 메시지 형식은 그대로 둬서 로봇과 웹 파트는 연결 주소만 바꾸면 되게 했습니다.

다시 연결된 로봇이 오프라인으로 보였습니다

로봇이 재접속하면 새 연결이 먼저 등록되고, 그 뒤에 늦게 도착한 옛 연결의 종료 처리가 새 연결 정보까지 지워 버렸습니다. 새 연결을 등록하기 전에 옛 연결부터 정리하도록 순서를 바꿨습니다. 아무 신호 없이 끊긴 경우를 대비해, 상태 메시지가 15초 동안 없으면 오프라인으로 봅니다.

영상이 끊기고, 고친 뒤에도 6초 늦었습니다

처음에는 영상을 STOMP로 보냈는데, 버퍼가 차면서 연결이 끊어졌습니다. 팀과 함께 영상을 제어 채널과 다른 길로 빼냈지만, 그때 쓴 HLS는 6초쯤 늦게 나와서 원격 조종에는 쓸 수 없었습니다. 제가 웹 재생을 WebRTC(WHEP)로 바꾸는 일을 맡았고, 바꾼 뒤에는 탐지 박스를 영상에 맞추는 보정값을 6초에서 0.3초로 줄여 운영했습니다.

02 / 여행 계획 서비스

가볼래 GABOLLE

2026.08 ~ 진행 중, 6인 팀

SSAFY 특화프로젝트 우수상

외국인 여행객이 취향과 이동 조건에 맞춰 부산 여행 일정을 만드는 서비스입니다. 저는 여행과 일정 API를 맡아, 재요청으로 여행이 중복 생성되거나 동행자의 수정이 서로 덮이거나 이벤트 기록이 사라지는 문제를 DB 단에서 막았습니다.

제 담당
여행과 일정 API, PostgreSQL 저장과 검증, 이벤트 저장 경로 수정
사용 기술
Java 17, Spring Boot, JPA, PostgreSQL, Flyway
  • 재요청해도 여행은 하나만Idempotency-Key를 DB에 먼저 등록한 요청만 여행을 만들고, 같은 요청에는 기존 결과를 돌려줍니다.
  • 동시 수정해도 변경이 사라지지 않게읽은 버전과 DB 버전이 같을 때만 수정하고, 충돌하면 409로 최신 일정을 다시 받게 했습니다.
  • 재시작해도 남는 이벤트 기록메모리에 쌓이던 사용자 이벤트를 PostgreSQL Outbox 테이블에 저장하도록 바꿨습니다.
  • 팀원들의 AI가 같은 파일을 고치지 않게고치기 전에 파일을 먼저 예약하는 팀 도구 axMap을 함께 만들었습니다. 저는 예약이 서로 겹치는지 판단하는 규칙을 설계하고 검증했습니다. 자세히 보기
저장소와 전체 설명 ↗PostgreSQL 검증 ↗

대표 사례

여행 만들기를 다시 누르면 여행이 두 개 생겼습니다

  1. 무슨 일이

    휴대폰이 서버 응답을 못 받으면 사용자는 같은 요청을 한 번 더 보냅니다. 처음 코드는 “이 요청 키가 이미 있나?”를 조회해 보고, 없으면 여행을 저장했습니다.

  2. 왜 그랬나

    같은 키의 요청 두 개를 동시에 보내 보니, 둘 다 “아직 없네”라고 보고 여행을 하나씩 만들었습니다. 조회하고 저장하는 사이의 짧은 틈이 문제였습니다.

  3. 고민한 점

    서버 안에서 락을 걸면 서버가 여러 대일 때는 소용이 없습니다. 그래서 모든 서버가 같이 쓰는 DB에 판단을 맡기기로 했습니다.

  4. 바꾼 방법

    요청 키를 먼저 DB에 넣어 보고, 들어간 요청만 여행을 만듭니다. 이미 있는 키라면 같은 내용일 때 기존 결과(200)를, 다른 내용일 때 409를 돌려줍니다.

  5. 한 번 더 막힌 곳

    같은 방식을 일정 충돌에도 쓰면서 SAVEPOINT로 예외를 복구했는데, 메모리 테스트는 통과하고 실제 PostgreSQL 테스트에서만 실패했습니다. 예외를 복구하는 대신 ON CONFLICT DO NOTHING으로 저장된 행이 0개인지 보고 충돌을 판단하게 바꿨습니다.

  6. 결과

    같은 키로 요청 8건을 동시에 보내도 여행은 1건만 생깁니다. 일정 충돌 처리는 실제 PostgreSQL 통합 테스트로 확인합니다.

  7. 아직 남은 일

    동시 요청 테스트는 아직 메모리 저장소에서만 돌립니다. 실제 PostgreSQL에서 동시 요청을 다시 확인하는 것이 다음 할 일입니다.

발표회가 끝난 뒤에도 이어 가는 서비스

SSAFY 프로젝트 기간(2026.08 ~ 09)이 끝난 뒤에도 팀이 앱 업데이트를 이어 가고 있습니다. FLY ASIA 전에는 시연 녹화에서 나온 앱 문제를 먼저 고쳐 전시에 대비했습니다.

그 밖의 문제 해결펼쳐 보기

동행자 두 명이 동시에 고치면 앞사람의 변경이 지워졌습니다

두 사람이 같은 일정을 보고 고치면, 나중에 저장한 사람이 앞사람의 변경을 덮어씁니다. 그래서 요청에 “내가 본 버전”을 함께 보내고, DB의 최신 버전과 같을 때만 수정되게 했습니다. 버전이 다르면 409를 돌려줘 최신 일정을 다시 받게 합니다. 동시 수정 8건을 보내면 1건만 성공하고 7건은 거절되는지 테스트로 확인했습니다.

성공 응답을 받았는데 이벤트 기록이 사라졌습니다

API는 “저장했다”고 응답하는데, 서버를 껐다 켜면 사용자 행동 기록이 전부 사라졌습니다. 실제 DB가 아니라 메모리 저장소에 쌓이고 있었습니다. 기록이 PostgreSQL Outbox 테이블로 들어가도록 저장 경로를 이었습니다. Outbox 구조는 팀이 함께 설계했고, 저는 이벤트를 받아 저장하는 경로를 맡았습니다.

axMap: 팀원들의 AI가 같은 파일을 고치지 않게 하는 도구펼쳐 보기

한 줄로 말하면, 파일 예약 장부입니다. 회의실을 쓰기 전에 예약하듯, AI 코딩 도구가 파일을 고치기 전에 “이 파일은 제가 쓸게요”라고 장부에 먼저 적습니다. 다른 사람이 이미 예약한 파일이면 시작 전에 막고, 누가 언제까지 쓰는지 알려 줍니다. 저는 이 중에서 “지금 예약하려는 파일이 남의 예약과 겹치는가”를 판단하는 규칙을 설계하고, 만들어진 코드가 규칙대로 동작하는지 검증했습니다.

왜 만들었나

가볼래 팀은 여섯 명이 각자 AI 코딩 도구를 띄워 개발했습니다. 그러다 보니 누가 어떤 파일을 고치는지 서로 보이지 않았고, 같은 파일을 동시에 고친 사실은 코드를 합칠 때가 돼서야 알게 됐습니다. 그래서 팀 회의에서 “고치기 전에 먼저 예약하자”는 규칙을 정했고, 이 규칙을 사람이 아니라 도구가 지키게 만든 것이 axMap입니다.

어디까지를 ‘겹친다’고 볼까

같은 파일이거나, 한쪽이 다른 쪽을 품은 폴더라면 겹친다고 봤습니다. A가 src/auth 폴더를 예약했다면 그 안의 src/auth/login.ts는 막힙니다. 그런데 이름만 비슷한 src/authz는 전혀 다른 폴더라 통과해야 합니다. 글자 앞부분만 비교하면 이것까지 막히기 때문에, 경로를 / 단위로 잘라 폴더 이름끼리 비교하도록 정했습니다. ./src/auth/처럼 적는 방식만 다른 경로는 같은 경로로 맞추고, 저장소 밖을 가리키는 경로는 받지 않습니다.

막을 때는 이유까지 알려 줍니다

“실패”라고만 하면 AI는 같은 요청을 계속 다시 보냅니다. 그래서 누가, 무슨 작업으로, 몇 분 더 쓰는지를 함께 보여 주고, 일반 오류(1)와 구분되는 종료 코드 2를 돌려줘 AI가 다른 작업으로 넘어가게 했습니다. 판단 로직은 입력만 보고 결과를 내도록 따로 떼어 두자고 제안했는데, 덕분에 두 사람이 거의 동시에 예약했을 때 최신 장부로 다시 판단하는 데도 그대로 쓸 수 있었습니다. 동시 예약 처리와 장부 동기화는 팀원들과 함께 설계했습니다.

얼마나 쓰였고, 무엇을 못 하나

가볼래 개발 기간(2026.08.25 ~ 09.30)에 예약 3,629회, 반납 2,224회가 장부에 쌓였습니다. npm에도 공개해 누적 다운로드 23,794회를 기록했습니다(npm 공식 통계 기준). 다만 예약을 무시하고 파일을 고치는 것까지 막지는 못하고, 서로 다른 파일에 같은 기능을 만드는 중복도 잡지 못합니다.

커밋 작성자가 한 명인 이유

AI로 도구를 만드는 데 토큰 비용이 많이 들어, 팀 회의에서 한 사람의 개인 계정(Claude Max 구독)으로만 코드를 생성하기로 정했습니다. 나머지 팀원은 구조와 기능별 구현 방식을 회의로 함께 정하고, 결과를 검토하는 방식으로 참여했습니다. 그래서 공개 저장소에는 커밋 작성자가 팀원 한 명으로 나옵니다.

조리 로봇이 사람의 요리 영상을 보고 배우려면, 몇 초부터 몇 초까지가 어떤 동작인지 표시한 데이터가 필요합니다. 로보터블과 함께 이 동작 구간의 경계를 찾는 파이프라인을 만들고 있습니다. 볶는 동안처럼 비슷한 장면이 이어지는 구간까지 모두 시각언어모델(VLM)에 보내면 비용이 커서, 장면을 적게 보내면서도 경계를 놓치지 않는 것이 핵심입니다. 저는 VLM에 무엇을 보낼지 바꾸는 실험과, 팀에서 나온 점수가 사람이 검수한 정답에서도 유지되는지 확인하는 일을 맡고 있습니다.

대표 사례

AI 라벨에서 0.79였던 점수가 사람 정답에서는 무작위와 같았습니다

  1. 무엇을 봤나

    팀에서 AI가 붙인 라벨로 경계 검출 모델을 다시 학습해, 교차검증 F1(±3초)을 0.286에서 0.792로 올렸다는 결과가 나왔습니다. 그런데 이 점수는 학습에 쓴 것과 같은 AI 라벨로 매긴 점수였습니다.

  2. 어떻게 확인했나

    모델은 고치지 않고 사람이 검수한 16편에 그대로 적용했습니다. 경계를 많이 낼수록 점수가 저절로 오르기 때문에, 영상마다 같은 개수의 시각을 무작위로 찍은 기준선(50회 평균)을 함께 채점했습니다. 같은 정답과 매칭 코드로 Gemini 판독 결과도 한 표에 놓았습니다.

  3. 결과

    F1은 0.204로, 같은 개수 무작위 0.196과 거의 같았습니다. 놓친 경계는 적었지만(재현율 0.954) 낸 경계의 89%가 정답과 맞지 않았습니다(정밀도 0.114).

  4. 왜 그랬나

    AI 라벨은 손을 옮기거나 잠깐 멈추는 순간까지 경계로 세서 분당 23.4개를 학습시켰고, 모델도 분당 31.9개를 냈습니다. 사람 정답은 분당 3.8개였습니다. 무엇을 경계로 볼지부터 달랐던 것입니다.

  5. 제안

    사람 정답에 맞춰 임계값을 다시 골라도 0.50 안팎으로, 비슷한 개수를 내는 Gemini 판독(0.626)보다 낮았습니다. 그래서 모델을 그대로 쓰기보다 학습 라벨의 경계 기준을 사람 쪽(분당 약 4개)에 맞추는 일을 먼저 하자고 제안했습니다. 조리 단계 중심 규칙으로 라벨을 바꿔 다시 학습하자 0.204가 0.385로 오른 것이 근거입니다.

  6. 아직 남은 일

    16편에서 조건마다 1회씩 실행한 결과이고, 학습 라벨 기준은 팀 결정이 남아 있습니다. 사람이 검수한 라벨로 학습과 평가를 나눠 다시 확인하는 것이 다음 할 일입니다.

영상 조각이 사진보다 싼 이유

Gemini의 동영상 저해상도 모드는 프레임당 약 70토큰으로, 사진 한 장(약 550토큰)보다 훨씬 쌉니다. 화면 위쪽 띠에 원본 시각을 새겨 모델이 시각을 정확히 적게 했고, 조각을 120초로 늘려 호출마다 붙는 프롬프트 비용도 줄였습니다. 사람이 초안을 검수하는 용도라면 놓친 경계를 찾기보다 틀린 경계를 지우는 편이 쉬워서, “젓기와 그대로 익히기 사이도 새 구간” 지시를 더해 재현율을 0.66에서 0.87로 올린 조건도 함께 제안했습니다.

목표 0.90에 못 미친 이유를 찾았습니다

기업이 준 정답 15편으로 임베딩과 변화점 탐지, 지도학습 TCN과 GRU, 행동 인식 특징(X3D), 미세조정한 CLIP까지 비교했습니다. 가장 좋은 조합은 두 모델의 점수 평균으로 F1(±3초) 0.800이었습니다. 정답을 뜯어보니 경계의 91%가 불 조절, 투입, 젓기, 뒤집기, 그대로 익히기처럼 동작 상태가 바뀌는 지점이었습니다. 상태를 초 단위로 정확히 알면 0.943까지 가능한데 지금 모델의 상태 정확도가 약 0.80이라, 경계보다 상태 판독을 먼저 올려야 한다고 정리했습니다.

효과가 없었던 것도 남겼습니다

움직임 신호로 프레임을 더 줄이면, 조리 중에는 젓느라 화면이 늘 움직여 경계를 놓쳤습니다. 두 번 판독해 투표로 합치는 방법은 토큰이 두 배인데 얻는 것이 작았습니다. 손과 물체 탐지(YOLO, MediaPipe)에 로컬 VLM을 잇는 5단계 파일럿은 재료 투입을 하나도 찾지 못해 채택을 보류했습니다. 실패한 조건도 코드와 호출 기록을 함께 남겨, 팀이 같은 시도를 반복하지 않게 했습니다.

사람끼리도 경계를 다르게 긋습니다

다른 사람이 단 라벨을 예측처럼 놓고 채점해도 F1(±5초)은 0.694였습니다. 그래서 점수가 0.7을 넘은 뒤에는 남은 오차의 상당 부분이 정답 작성 방식 차이일 수 있다고 보고, 재료 투입을 시작만 적을지 끝까지 적을지 같은 라벨 표기 기준을 팀에서 맞추자고 제안했습니다.

AI 도구를 쓴 방식

실험 코드 작성과 실행에는 Claude Code를 썼습니다. 저는 무엇을 비교할지, 같은 정답과 같은 매칭 코드와 무작위 기준선처럼 어떤 조건에서 비교할지를 정하고 결과와 기록을 확인했습니다. 실험마다 코드 커밋, 입력 해시, 모델 설정과 실제 사용 토큰을 남겨 다른 팀원이 같은 결과를 다시 낼 수 있게 했습니다.

특정 시간대만 되면 캠퍼스 주차장에서 빈자리를 찾느라 스트레스를 받는다는 이야기를 자주 들었습니다. 주차면마다 센서를 달면 장비와 설치에 비용이 많이 들어, 카메라 영상만으로 풀어 보고 싶었습니다. 그렇게 만든 서비스가 빈자리입니다. 주차장 영상을 주차면별 상태로 바꿔 앱에 빈자리 수와 시간대별 통계를 보여 줍니다. 저는 분석 서버를 맡아, 차가 잠깐 가려져도 상태가 흔들리지 않는 판정 로직을 만들었습니다.

앱 연결 확인

문제 해결과 검증 근거펼쳐 보기

빈자리로 바꿀 때 더 깐깐하게 본 이유

차가 있는 자리를 비었다고 안내하면, 운전자는 그 자리까지 갔다가 헛걸음을 합니다. 그래서 차가 잠깐 가려졌다고 바로 빈자리로 바꾸지 않게 했습니다. 차가 들어온 건 5번, 빠진 건 8번 연속으로 확인해야 바뀝니다. 출차가 조금 늦게 반영되더라도 잘못된 안내를 줄이는 쪽을 골랐습니다.

탐지 박스 수를 그대로 빈자리 수로 쓰지 않았습니다

모델이 찾은 차량 박스는 옆 주차면까지 걸쳐 있을 때가 많습니다. 그래서 주차면마다 박스와 얼마나 겹치는지, 모델이 얼마나 확신하는지를 함께 보고 어느 자리의 차인지 정했습니다. 최근 10번의 판단과 위의 전환 기준을 거쳐 확정된 상태만 SQLite에 저장하고, 앱은 API로 이 값을 가져갑니다.

끝난 뒤 다시 보니 틀린 데이터가 있었습니다

기록이 없는 시간대에도 아무 값으로 혼잡도가 채워져 있었습니다. 5분마다 남긴 관측 기록이 있는 시간만 집계하고, 기록이 없으면 has_data=false로 따로 표시하게 고쳤습니다. 또 두 주차장이 같은 주차면 ID를 같이 쓰고 있어서, 기본키를 (parking_lot, id)로 바꿔 주차장별로 나눴습니다.
