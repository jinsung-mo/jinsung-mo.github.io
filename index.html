트러블슈팅 (프로젝트 종료 후 개인 작업)

외래키가 없어 잘못된 참조가 그대로 저장되던 문제

  1. 문제

    프로젝트가 끝나고 ERD를 다시 그려 보니, 테이블 사이에 외래키가 하나도 없었습니다. 실제로 없는 이벤트 ID로 영상을 등록해도 API가 아무 문제 없이 받아 주고 있었습니다.

  2. 해결

    외래키를 모든 관계에 똑같이 걸지는 않았습니다. 대신 “이벤트가 지워지면 이 데이터는 어떻게 돼야 하지?”를 관계마다 따져 봤습니다. 이벤트가 없으면 의미가 없는 알림 발송 기록은 같이 지우고(CASCADE), 증거로 남아야 하는 영상은 연결만 끊었습니다(SET NULL).

  3. 고려한 점

    경보가 가리키는 설비와 지도에는 외래키를 걸지 않았습니다. 로봇이 아직 등록되지 않은 설비 기준으로 경보를 보내면, 외래키 때문에 저장 자체가 실패하기 때문입니다. 화재 경보를 통째로 잃는 것보다는 참조가 조금 어긋나도 남아 있는 편이 낫다고 봤습니다.

  4. 결과

    스키마를 Flyway로 옮기고, 테스트 220건이 GitHub Actions에서 실제 MySQL 8 위로 자동 실행되게 했습니다. 처음에 봤던 영상 등록 문제가 이 테스트에서 걸려, 지금은 400으로 거절합니다.

  5. 남은 과제

    알림 워커가 외부 HTTP 호출을 트랜잭션 안에서 하고 있어서, 알림을 보낸 뒤 커밋이 실패하면 같은 알림이 두 번 나갈 수 있습니다. 외부 호출을 트랜잭션 밖으로 빼는 것이 다음 할 일입니다.

배포 서버 방화벽에 로봇 연결이 막혔습니다

로봇 통신을 TCP 9000번 포트로 만들었는데, 막상 배포해 보니 서버가 이 포트를 막고 있었습니다. 그래서 Nginx를 거쳐 443번 포트로 들어오는 WSS로 바꿨습니다. 메시지 형식은 그대로 둬서 로봇과 웹 파트는 연결 주소만 바꾸면 되게 했습니다.

다시 연결된 로봇이 오프라인으로 보였습니다

로봇이 재접속하면 새 연결이 먼저 등록되고, 그 뒤에 늦게 도착한 옛 연결의 종료 처리가 새 연결 정보까지 지워 버렸습니다. 새 연결을 등록하기 전에 옛 연결부터 정리하도록 순서를 바꿨습니다. 아무 신호 없이 끊긴 경우를 대비해, 상태 메시지가 15초 동안 없으면 오프라인으로 봅니다.

영상이 끊기고, 고친 뒤에도 6초 늦었습니다

처음에는 영상을 STOMP로 보냈는데, 버퍼가 차면서 연결이 끊어졌습니다. 팀과 함께 영상을 제어 채널과 다른 길로 빼냈지만, 그때 쓴 HLS는 6초쯤 늦게 나와서 원격 조종에는 쓸 수 없었습니다. 제가 웹 재생을 WebRTC(WHEP)로 바꾸는 일을 맡았고, 바꾼 뒤에는 탐지 박스를 영상에 맞추는 보정값을 6초에서 0.3초로 줄여 운영했습니다.

02 / 여행 계획 서비스

가볼래 GABOLLE

2026.08 ~ 09, 6인 팀

SSAFY 특화프로젝트 우수상

외국인 여행객이 취향과 이동 조건에 맞춰 부산 여행 일정을 만드는 서비스입니다. 저는 여행과 일정 API를 맡아, 재요청으로 여행이 중복 생성되거나 동행자의 수정이 서로 덮이거나 이벤트 기록이 사라지는 문제를 DB 단에서 막았습니다. 앱의 AI 챗봇 ‘동백이’ 서버도 처음 설계해 만들었습니다.

맡은 역할
여행과 일정 API, PostgreSQL 저장과 검증, 이벤트 저장 경로 수정, AI 챗봇 서버
사용 기술
Java 17, Spring Boot, JPA, PostgreSQL, Flyway, Gemini API

해결한 문제

  • 같은 요청을 다시 보내도 여행은 1개만 생성Idempotency-Key를 DB에 먼저 등록한 요청만 여행을 만들고, 같은 요청에는 기존 결과를 돌려줍니다.
  • 두 사람이 동시에 고쳐도 변경이 사라지지 않게읽은 버전과 DB 버전이 같을 때만 수정하고, 충돌하면 409로 최신 일정을 다시 받게 했습니다.
  • 서버를 재시작하면 사라지던 이벤트 기록을 DB에 저장메모리에 쌓이던 사용자 이벤트를 PostgreSQL Outbox 테이블에 저장하도록 바꿨습니다.
  • AI 챗봇이 부산이 아닌 서울 가게를 추천하지 않게부산 여행 앱인데 모델이 학습한 지식으로 서울에 있는 가게를 추천했습니다. 답장은 모델 대신 서버가 조립하고, 챗봇은 화면 안내·여행 문장·도움말 세 가지로만 답하게 좁혔습니다. 버스 도착 시간과 환율도 직접 말하지 않고 실제 데이터를 보여 주는 화면으로 안내합니다. 자세히 보기

트러블슈팅

같은 요청이 동시에 오면 여행이 중복 생성되던 문제

  1. 문제

    휴대폰이 서버 응답을 못 받으면 사용자는 같은 요청을 한 번 더 보냅니다. 처음 코드는 “이 요청 키가 이미 있나?”를 조회해 보고, 없으면 여행을 저장했습니다.

  2. 원인

    같은 키의 요청 두 개를 동시에 보내 보니, 둘 다 “아직 없네”라고 보고 여행을 하나씩 만들었습니다. 조회하고 저장하는 사이의 짧은 틈이 문제였습니다.

  3. 고려한 점

    서버 안에서 락을 걸면 서버가 여러 대일 때는 소용이 없습니다. 그래서 모든 서버가 같이 쓰는 DB에 판단을 맡기기로 했습니다.

  4. 해결

    요청 키를 먼저 DB에 넣어 보고, 들어간 요청만 여행을 만듭니다. 이미 있는 키라면 같은 내용일 때 기존 결과(200)를, 다른 내용일 때 409를 돌려줍니다.

  5. 추가 문제

    같은 방식을 일정 충돌에도 쓰면서 SAVEPOINT로 예외를 복구했는데, 메모리 테스트는 통과하고 실제 PostgreSQL 테스트에서만 실패했습니다. 예외를 복구하는 대신 ON CONFLICT DO NOTHING으로 저장된 행이 0개인지 보고 충돌을 판단하게 바꿨습니다.

  6. 결과

    같은 키로 요청 8건을 동시에 보내도 여행은 1건만 생기고, 나머지 7건은 같은 여행을 돌려받습니다. 프로젝트 후 실제 PostgreSQL에서도 동시 요청 테스트로 다시 확인했습니다.

수상과 전시

SSAFY 프로젝트 기간(2026.08 ~ 09)이 끝난 뒤에도 팀이 앱 업데이트를 이어 가고 있습니다. FLY ASIA 전에는 시연 녹화에서 나온 앱 문제를 먼저 고쳐 전시에 대비했습니다.

트러블슈팅 더 보기 (2건)펼쳐 보기

동행자 두 명이 동시에 고치면 앞사람의 변경이 지워졌습니다

두 사람이 같은 일정을 보고 고치면, 나중에 저장한 사람이 앞사람의 변경을 덮어씁니다. 그래서 요청에 “내가 본 버전”을 함께 보내고, DB의 최신 버전과 같을 때만 수정되게 했습니다. 버전이 다르면 409를 돌려줘 최신 일정을 다시 받게 합니다. 동시 수정 8건을 보내면 1건만 성공하고 7건은 거절되는지 테스트로 확인했고, 프로젝트 후 실제 PostgreSQL에서도 같은 결과를 확인했습니다.

성공 응답을 받았는데 이벤트 기록이 사라졌습니다

API는 “저장했다”고 응답하는데, 서버를 껐다 켜면 사용자 행동 기록이 전부 사라졌습니다. 실제 DB가 아니라 메모리 저장소에 쌓이고 있었습니다. 기록이 PostgreSQL Outbox 테이블로 들어가도록 저장 경로를 이었습니다. Outbox 구조는 팀이 함께 설계했고, 저는 이벤트를 받아 저장하는 경로를 맡았습니다.

동백이에게 자연어로 물으면, 서버가 질문을 세 가지 답 중 하나로 바꿔 돌려줍니다. 알맞은 앱 화면으로 보내는 안내, 여행지에서 바로 쓸 한국어 문장, 서비스 사용법 도움말입니다. 저는 이 챗봇의 서버 API를 처음 설계하고 만들었습니다(2026.09.10 ~ 09.21). 대화 화면은 팀원들이 만들었습니다.

어떻게 만들었나

모델에게 자유로운 문장 대신 정해진 JSON 형식으로만 답하게 하고(구조화 출력), 서버가 그 값을 검증해 앱에 내려줍니다. 모델 호출은 AssistantVendorPort 인터페이스 뒤에 두었습니다. 그래서 Claude Haiku 4.5로 만든 첫 버전을 무료로 쓸 수 있는 Google Gemini로 바꿀 때 어댑터 하나만 갈아 끼웠고, 서비스와 컨트롤러는 그대로였습니다.

대화, 언어, 내 일정

대화는 서버에 저장하지 않고, 앱이 최근 몇 턴을 함께 보냅니다. 답변 언어는 Accept-Language로 맞추고, 사용자마다 1분에 10번까지만 받아 넘으면 429를 돌려줍니다. 사용자가 동의하고 일정을 골랐을 때만 그날 일정을 읽어 답에 쓰고, 알레르기 같은 건강 정보는 모델에 보내지 않습니다.

트러블슈팅: 챗봇이 부산이 아닌 서울에 있는 가게를 추천했습니다

문제 첫 버전은 대화에서 여행 조건을 뽑고, 사용자에게 보이는 답장은 모델이 자유롭게 썼습니다. 그러자 부산 여행 앱인데 서울에 있는 가게를 추천하는 답이 나왔습니다. 모델이 가볼래 데이터가 아니라 자기가 학습한 지식으로 답한 것입니다. 가볼래는 설문과 현지인 추천으로 모은 실제 부산 장소를 추천하는 서비스라, 이런 답은 서비스의 근거를 무너뜨립니다. 프롬프트로 금지해도 모델이 쓴 문장이 그대로 나가는 한 통로는 남아 있었습니다.

해결 지어낸 내용이 나갈 길을 구조로 막았습니다. 먼저 답장은 모델이 채운 값(지역, 인원, 음식 취향)만으로 서버가 조립하게 했고, 이어서 일정을 대신 짜는 기능 자체를 빼 은행 앱 챗봇처럼 안내만 하게 좁혔습니다. 화면 안내는 서버의 허용 목록에 있는 다섯 화면으로만 보내고, 버스 도착 시간이나 환율처럼 매번 바뀌는 숫자는 직접 말하지 않고 실제 값을 보여 주는 화면으로 안내합니다.

결과 실제 Gemini를 호출해 확인해 보니, 장소 추천을 요청해도 이름을 지어내지 않고 여행 만들기 화면으로 안내했고, 범위 밖 질문은 거절했습니다.

구조화 출력에서 뒤쪽 값이 빠졌습니다

응답 형식을 Map.of()로 넘기면 필드 순서가 보장되지 않아, 모델이 뒤쪽 필드(여행 일수, 인원)를 빠뜨리는 경우가 있었습니다. propertyOrdering으로 순서를 명시해 고쳤고, 버튼 문구가 비어 오면 화면별 기본 문구를 쓰게 했습니다.

챗봇 버튼이 앱에서 사라지지 않게

앱은 모르는 화면 주소의 버튼을 지우는데, 서버 목록을 손으로 베껴 검사하다 보니 챗봇 이동 버튼 세 개가 사라진 일이 있었습니다. 서버의 허용 목록과 앱의 화면 목록을 원본 파일끼리 대조하는 CI 검사를 만들어, 서버가 보낼 수 있는 주소를 앱이 모르면 검사가 실패하게 했습니다.

빈자리로 바꿀 때 더 깐깐하게 본 이유

차가 있는 자리를 비었다고 안내하면, 운전자는 그 자리까지 갔다가 헛걸음을 합니다. 그래서 차가 잠깐 가려졌다고 바로 빈자리로 바꾸지 않게 했습니다. 차가 들어온 건 5번, 빠진 건 8번 연속으로 확인해야 바뀝니다. 출차가 조금 늦게 반영되더라도 잘못된 안내를 줄이는 쪽을 골랐습니다.

탐지 박스 수를 그대로 빈자리 수로 쓰지 않았습니다

모델이 찾은 차량 박스는 옆 주차면까지 걸쳐 있을 때가 많습니다. 그래서 주차면마다 박스와 얼마나 겹치는지, 모델이 얼마나 확신하는지를 함께 보고 어느 자리의 차인지 정했습니다. 최근 10번의 판단과 위의 전환 기준을 거쳐 확정된 상태만 SQLite에 저장하고, 앱은 API로 이 값을 가져갑니다.

끝난 뒤 다시 보니 틀린 데이터가 있었습니다

기록이 없는 시간대에도 아무 값으로 혼잡도가 채워져 있었습니다. 5분마다 남긴 관측 기록이 있는 시간만 집계하고, 기록이 없으면 has_data=false로 따로 표시하게 고쳤습니다. 또 두 주차장이 같은 주차면 ID를 같이 쓰고 있어서, 기본키를 (parking_lot, id)로 바꿔 주차장별로 나눴습니다.
