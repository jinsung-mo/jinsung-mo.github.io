대표 사례 · 증상에서 원인까지

여행 만들기를 다시 누르면 여행이 두 개 생겼습니다

  1. 증상

    휴대폰이 서버 응답을 받지 못하면 사용자는 같은 요청을 다시 보냅니다. 처음에는 요청 키가 이미 있는지 조회한 뒤 여행을 저장했습니다.

  2. 원인 추적

    동시 요청 테스트에서 같은 키의 요청 두 개가 동시에 들어오면, 둘 다 “키가 없다”고 판단해 여행을 각각 만들었습니다. 조회와 저장 사이의 틈이 원인이었습니다.

  3. 검토한 방법

    애플리케이션 락도 고려했지만, 서버가 여러 대면 락이 서버마다 따로 잡혀 소용이 없어 제외했습니다. 모든 서버가 공유하는 DB가 판단하게 하기로 했습니다.

  4. 선택

    요청 키를 먼저 INSERT해 확보한 요청만 여행을 만듭니다. 같은 키·같은 내용이면 기존 결과(200)를, 내용이 다르면 409를 돌려줍니다. 동시 요청 8건에서 여행은 1건만 생성됩니다.

  5. 다시 의심한 것

    같은 방식을 일정 충돌 처리에 적용하며 SAVEPOINT를 썼는데, 메모리 테스트는 통과하고 PostgreSQL 통합 테스트에서만 실패했습니다. 예외 후 복구하는 대신 ON CONFLICT DO NOTHING으로 저장된 행이 0개인지를 보고 충돌을 판단하도록 바꿨습니다.

  6. 남은 과제

    동시 요청 테스트는 아직 메모리 저장소 기반입니다. 실제 PostgreSQL에서 동시 요청을 다시 검증하는 것이 다음 과제입니다.

대표 사례 · 프로젝트 종료 후 개인 작업

화재 경보가 참조 오류로 저장되지 않을 수 있었습니다

  1. 발견

    프로젝트가 끝난 뒤 ERD를 다시 그려 보니 테이블 사이에 DB 외래키가 하나도 없었습니다. 확인해 보니 없는 이벤트 ID로 영상을 등록해도 API가 그대로 받아 주고 있었습니다.

  2. 판단

    외래키를 모든 관계에 똑같이 걸지 않고, 삭제됐을 때 어떻게 되어야 하는지를 관계마다 정했습니다. 이벤트가 지워지면 의미가 없는 알림 발송 기록은 함께 삭제(CASCADE)하고, 증거로 남아야 하는 영상은 연결만 끊었습니다(SET NULL).

  3. 걸지 않은 외래키

    경보가 참조하는 설비·지도에는 일부러 외래키를 걸지 않았습니다. 로봇이 등록되지 않은 설비를 기준으로 경보를 보내면 INSERT 자체가 실패하기 때문입니다. 화재 경보를 참조 오류로 잃는 것보다 어긋난 참조라도 남는 편이 낫다고 판단했고, 이런 경보는 정기 점검 쿼리로 찾아내도록 했습니다.

  4. 검증

    스키마를 Flyway로 옮기고 전체 테스트 220건을 실제 MySQL 8에서 돌렸습니다. 앞의 영상 등록 문제가 테스트에서 드러나, 400으로 거절하도록 고쳤습니다.

  5. 남은 과제

    알림 워커가 외부 HTTP 호출을 트랜잭션 안에서 해서, 전송 후 커밋이 실패하면 중복 발송될 수 있습니다. 외부 호출을 트랜잭션 밖으로 빼는 구조가 다음 과제입니다.

재접속한 로봇이 오프라인으로 보였습니다

영상이 끊기고, 바꾼 뒤에도 6초 늦었습니다

처음에는 영상을 STOMP로 중계했는데, 버퍼가 차면서 연결이 끊겼습니다. 팀과 함께 영상 경로를 제어 채널에서 분리했지만, 중간에 쓴 HLS는 약 6초 지연이 있어 원격 조종에 쓸 수 없었습니다. 저는 웹 재생을 WebRTC(WHEP)로 전환하는 작업을 맡았습니다. 전환 후에는 탐지 박스를 영상에 맞추는 화면 보정값을 6초에서 0.3초로 낮춰 운영했습니다.

무선 환경에서 같은 경보가 여러 번 들어왔습니다

문제 해결과 검증 근거펼쳐 보기

비슷한 프레임의 반복 추론을 줄였습니다

주차 상태가 거의 달라지지 않는 연속 프레임에 같은 계산을 반복하고 있었습니다. 5프레임 중 1개만 모델로 분석하도록 바꿔 추론 횟수를 80% 줄였습니다.

왜 빈자리 전환을 더 엄격하게 했나

차량이 잠깐 가려졌다고 바로 빈자리로 바꾸지 않도록 했습니다. 주차된 자리를 비었다고 안내하면 운전자가 헛걸음을 합니다. 그래서 출차 반영이 조금 늦더라도, 점유 전환은 5회·빈자리 전환은 8회 확인하도록 빈자리 쪽 기준을 더 엄격하게 뒀습니다.

탐지 박스를 바로 빈자리 수로 세지 않았습니다

모델이 찾은 영역은 옆 주차면까지 걸칠 수 있습니다. 각 주차면과 탐지 박스가 겹치는 면적에 신뢰도를 반영해 어느 주차면의 결과인지 연결했습니다. 최근 10개 판정과 전환 기준을 거쳐 확정한 상태를 SQLite에 저장하고, 앱이 API로 조회하도록 했습니다.

종료 후 다시 보니 데이터가 틀린 곳이 있었습니다

기록이 없는 시간대에도 임의 값으로 혼잡도가 표시되고 있었습니다. 5분 간격 관측 기록이 있는 시간만 집계하고, 없으면 has_data=false로 구분했습니다. 두 주차장이 같은 주차면 ID를 쓰던 상태 테이블은 기본키를 (parking_lot, id)로 바꿔 주차장별로 나눴습니다.

통계 수정과 기록 재생 테스트는 프로젝트 종료 후 개인 작업입니다. 처리 시간 단축률과 전체 주차면 오탐률은 아직 측정하지 않았습니다.
