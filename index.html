01 / 여행 계획 서비스

가볼래 GABOLLE

2026.08 — 09 · 6인 팀

SSAFY 프로젝트 우수상

외국인 여행객이 취향과 이동 조건에 맞춰 부산 여행 일정을 만들고, 앱에서 경로를 확인하는 서비스입니다.

제 담당
여행·일정 API, PostgreSQL 저장·검증, 이벤트 수집 경로 수정
사용 기술
Java 17 · Spring Boot · JPA · PostgreSQL · Flyway
  • 중복 생성 방지DB에서 요청 키를 먼저 확보하고, 동일 요청에는 기존 여행을 반환합니다.
  • 일정 수정 충돌 처리버전이 일치할 때만 갱신하고, 충돌한 요청에는 409를 반환합니다.
  • 이벤트 저장 경로 수정메모리 저장소로 향하던 호출을 PostgreSQL Outbox 저장 경로로 연결했습니다.
저장소 · 전체 설명 ↗PostgreSQL 검증 ↗

검증한 범위

동시 요청 로직과 실제 DB 동작을 나눠 확인했습니다. 8개 동시 요청은 메모리 저장소로, PostgreSQL의 중복 키·버전 제약과 충돌 롤백은 별도 통합 테스트로 확인했습니다.

문제 해결과 검증 근거펼쳐 보기

재요청으로 여행이 중복 생성되는 문제

휴대폰이 응답을 받지 못해 같은 요청을 다시 보내도 여행이 늘어나지 않도록 했습니다. DB에 요청 식별자(Idempotency-Key)를 먼저 등록한 요청만 새 여행을 만듭니다. 같은 키와 내용이면 기존 여행을 돌려주고, 내용이 다르면 충돌로 거절합니다. 8개 동시 요청은 메모리 저장소로, 실제 PostgreSQL 제약은 별도 통합 테스트로 확인했습니다.

동시에 수정한 일정이 덮이지 않도록

동행자 두 사람이 같은 일정을 수정하면 늦게 저장한 내용이 앞사람의 변경을 지울 수 있습니다. 사용자가 읽은 버전을 요청에 담고, DB의 최신 버전과 일치할 때만 수정하도록 했습니다. 충돌하면 409를 반환해 최신 일정을 다시 확인하게 합니다. 실제 DB 테스트에서 오류가 난 중첩 트랜잭션 방식은 중복 저장을 건너뛰는 SQL과 조건부 갱신으로 바꿨습니다.

성공 응답 뒤에도 이벤트 기록이 사라졌습니다

사용자 행동 이벤트를 받는 API가 메모리 저장소를 사용해, 서버를 재시작하면 기록이 사라졌습니다. 저장소 호출을 추적해 PostgreSQL의 Outbox 테이블에 기록하도록 연결했습니다.

중복 생성 방지 코드 ↗일정 충돌 처리 코드 ↗이벤트 저장 코드 ↗

이벤트 관련 담당 범위는 수집·저장 경로 수정입니다. 공개본의 이벤트 발행자는 NoOpEventPublisher이며, Kafka 전달까지 구현한 결과로 제시하지 않습니다.

영상 지연을 통신 경로에서 줄였습니다

처음에는 STOMP 영상 중계의 버퍼가 차면서 연결이 끊겼습니다. 팀과 함께 영상 경로를 분리했지만, 중간에 사용한 HLS도 약 6초의 지연으로 원격 조종에 맞지 않았습니다. 저는 웹 재생을 WebRTC(WHEP)로 전환했습니다. 최종 약 0.3초는 관제 화면 보정값 기준이며, 영상 전체 구간을 직접 측정한 값과는 구분합니다.

재전송된 경보는 한 번만 저장합니다

무선 연결에서는 로봇이 같은 경보를 다시 보낼 수 있습니다. 재전송해도 유지되는 messageId와 MySQL 고유 제약으로 중복 저장을 막았습니다. DB 저장은 전용 비동기 작업으로 옮겼습니다. 대기열이 차면 수신 스레드가 직접 처리하므로, 경보를 버리지 않는 대신 수신이 늦어질 수 있습니다.

대기열이 차면 수신 스레드가 직접 저장을 처리하므로 수신이 지연될 수 있고, 큐 포화 상태의 전체 처리 순서까지 보장하지는 않습니다.

문제 해결과 검증 근거펼쳐 보기

비슷한 프레임의 반복 추론을 줄였습니다

주차 상태가 크게 달라지지 않는 연속 프레임에 같은 계산을 반복하고 있었습니다. 5프레임 중 1개만 모델로 분석하도록 바꿔 추론 대상을 설정상 약 80% 줄였습니다. 전체 처리 시간과 앱 반영 속도는 별도 측정이 필요합니다.

상태 전환에 서로 다른 확인 기준을 둡니다

차량이 잠깐 가려졌다고 바로 빈자리로 바꾸지 않도록 했습니다. 일반 주차면은 점유 전환을 5회, 빈자리 전환을 8회 확인합니다. 이미 주차된 자리를 비었다고 안내하면 운전자가 다시 찾아야 하므로 빈자리 전환에 더 엄격한 기준을 뒀습니다. 실제 출차도 늦게 반영될 수 있습니다.

탐지 박스를 바로 빈자리 수로 세지 않았습니다

모델이 찾은 영역은 옆 주차면까지 걸칠 수 있습니다. 각 주차면과 탐지 박스가 겹치는 면적에 신뢰도를 반영해 어느 주차면의 결과인지 연결했습니다. 최근 10개 판정과 전환 기준을 거쳐 확정한 상태를 SQLite에 저장하고, 앱이 API로 조회하도록 했습니다.

관측값만 쓰도록 통계를 수정한 일과 기록 재생 테스트는 프로젝트 종료 후 개인 작업입니다. 전체 주차면의 오탐률과 상태 전환 지연은 추가 평가가 필요합니다.
