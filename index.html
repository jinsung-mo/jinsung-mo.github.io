CASE 01

연결이 끊겨 다시 보낸 요청도 여행 하나만 만들도록

문제
여행 생성 응답을 받지 못한 앱이 다시 요청하면 같은 여행이 중복 생성될 수 있었습니다.
원인
요청 키를 조회한 뒤 등록하면, 두 요청이 모두 조회를 통과하는 틈이 생깁니다.
선택
(user_id, idempotency_key) 고유 제약으로 키를 먼저 확보한 요청만 여행을 만들도록 했습니다. ON CONFLICT DO NOTHING으로 충돌을 처리하고, 같은 키와 내용이면 기존 결과를 반환합니다. 내용이 다르면 409로 거절합니다.
검증
중복 생성과 재요청은 메모리 저장소 테스트로, 키 선점과 DB 제약은 PostgreSQL 통합 테스트로 나누어 확인하도록 테스트를 작성했습니다.

CASE 02

먼저 저장한 동료의 일정이 덮이지 않도록

문제
동행자들이 같은 일정의 5번 버전을 보고 수정하면, 나중 요청이 앞선 변경을 덮어쓸 수 있었습니다.
선택
요청에 기준 버전 baseVersion을 받고, 중복 버전 INSERT는 처리 행 수로 판별했습니다. 최신 버전도 여전히 기준 버전과 같을 때만 조건부 UPDATE합니다. 충돌한 요청에는 409를 반환합니다.
막혔던 점
처음에는 SAVEPOINT로 충돌을 복구하려 했지만, 프로젝트 기록의 PostgreSQL 통합 테스트에서 중첩 트랜잭션 예외가 발생했습니다. 중복을 SQL 오류로 만들지 않는 ON CONFLICT DO NOTHING 방식으로 바꿨습니다.
검증
메모리 저장소의 8개 동시 요청 테스트는 1개 성공, 7개 거절, 5→6 전환, 7번 버전 미생성을 확인합니다. 중복 버전과 최신 버전 갱신 충돌은 별도의 PostgreSQL 통합 테스트로 검사합니다. 8개 동시 요청을 실제 DB에서 실행한 결과는 아닙니다.
충돌 처리 코드 ↗8개 동시 요청 테스트 ↗PostgreSQL 테스트 ↗
추가 사례 / 성공 응답 뒤 이벤트가 사라진 이유

이벤트 API가 DB 대신 메모리 저장소를 참조하고 있었습니다. 호출되는 구현을 추적해 PostgreSQL Outbox 저장 경로로 연결했습니다. 제 기여는 이 오류 분석과 저장 경로 통합이며, 전체 Outbox 설계나 Kafka 발행을 맡았다는 뜻은 아닙니다. 공개 main의 이벤트 발행자는 NoOp입니다.

이벤트 저장 코드 ↗

문제

선택
재전송해도 유지되는 messageId와 MySQL UNIQUE 제약으로 중복 저장을 막았습니다. 저장 작업은 별도 스레드 하나에서 순서대로 처리해 수신 작업과 분리했습니다.

CASE 02

경보 이력이 쌓인 뒤의 조회도 확인했습니다

범위

문제

선택
서버가 사용하는 조회에 맞춰 시간 인덱스와 로봇 ID + 시간 복합 인덱스를 추가했습니다. EXPLAIN ANALYZE로 실행 계획과 검사 행 수를 비교했습니다.
결과
최근 24시간 경보 통계 쿼리는 55.9ms → 4.9ms, 검사 행 수는 약 19.9만 → 6,642로 줄었습니다. MySQL 8.0.46, Apple M4 Pro, 합성 데이터 기준이며 6회 실행 중 첫 회를 제외한 중앙값입니다.

CASE 02

문제

선택
일반 주차면은 최근 10개 판정에 시간 가중치와 신뢰도를 반영합니다. 빈자리→점유는 5회, 점유→빈자리는 8회 확인하도록 기준을 나눴습니다. 신뢰도가 부족한 판정은 확인 횟수를 늘리지 않습니다.
이유
주차된 공간을 빈자리로 안내하면 사용자가 그 자리까지 갔다가 다시 찾아야 합니다. 빈자리로 바꿀 때 더 신중하도록 설계했습니다.
확인과 한계
B5 입차 구간을 모델로 다시 분석해 빈자리 수가 2→1로 바뀌는 결과를 확인했습니다. 같은 결과를 API로 재생해 앱 표시도 확인했습니다. 앱은 10초 간격으로 조회하며, 이 시연은 오탐률 개선이나 실시간 처리 지연의 측정 결과는 아닙니다.
