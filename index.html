삐용 BBIYONG

2D 공장 지도 생성부터 점검 지점 순찰·화재 관제까지 연결한 시스템

서비스

사람이 적은 시간에도 공장 안의 사각지대를 확인하기 위한 자율 순찰·관제 서비스입니다. 로봇이 공장을 자율주행하며 2D 지도를 만들고, 지도에 점검 지점을 지정하면 해당 지점들을 순찰합니다. 순찰 중 화재 징후를 확인하면 현장 영상과 경보를 웹 관제로 전달합니다.

  • 2D 지도 생성 → 점검 지점 지정 → 지정 지점 자율 순찰
  • RGB·열화상 화재 확인, 웹에서 위치·영상·경보 확인 및 원격 제어
담당
팀장 · Spring Boot 관제 서버, 로봇/웹 통신, 경보 저장·인증
기술
Java 17, Spring Boot, WebSocket, STOMP, MySQL 8, Docker

영상 지연을 통신 경로에서 줄였습니다

관제 서버의 STOMP로 영상을 중계할 때 약 6초 지연이 생겨 원격 조종이 어려웠습니다. 팀과 함께 영상 경로를 MediaMTX로 분리하고, 제가 웹 재생을 WebRTC(WHEP)로 전환했습니다. 프로젝트 기록의 최종 지연은 관제 화면 보정값 기준 약 0.3초입니다.

재전송된 경보는 한 번만 저장합니다

무선 연결에서는 로봇이 같은 경보를 다시 보낼 수 있습니다. 경보마다 바뀌지 않는 messageId를 붙이고 MySQL UNIQUE 제약으로 동시 저장 충돌을 막았습니다. 저장은 단일 스레드 비동기 작업으로 옮겨 수신을 막지 않으면서 순서를 지켰습니다.

팀 프로젝트 이후 · 개인 개선

20만 건의 합성 이벤트를 MySQL 8에서 조회하며 인덱스를 검증했습니다. 최근 24시간 경보 통계는 55.9ms에서 4.9ms로 줄었습니다(첫 실행을 제외한 5회 중앙값). Flyway 마이그레이션과 서버 테스트 220건의 CI도 보강했습니다. 이 변경은 팀 배포 서버에 반영하지 않았습니다.

로봇 주행과 AI 모델 최적화는 다른 팀원이 맡았습니다. 위 인덱스·Flyway·CI 개선은 팀 프로젝트 종료 후 개인 작업입니다.

여행 계획 서비스 · 6인 팀

가볼래 GABOLLE

부산 현지인이 찾는 맛집과 여행지를 여행 조건에 맞춰 추천하는 서비스

서비스

외국인 관광객은 유명 관광지 밖에서 부산 주민들이 실제로 찾는 맛집과 여행지를 고르기 어렵습니다. 가볼래는 부산에서 10년 이상 거주한 주민과 부산에서 활동하는 택시기사의 설문 응답으로 장소 데이터를 확보하고, 이를 여행 추천에 반영한 서비스입니다. 여행자는 날짜·예산·취향·이동 조건을 입력해 코스를 고르고 일정과 경로를 확인합니다.

  • 현지 설문 기반 맛집·여행지 정보를 추천에 반영
  • 여행 조건 입력 → 코스 선택 → 일정·이동 경로 확인
담당
여행·일정 백엔드, PostgreSQL 저장·검증, AI 여행 도우미 서버 기능
기술
Java 17, Spring Boot, JPA, PostgreSQL, Flyway

재요청으로 여행이 중복 생성되는 문제

모바일 연결이 끊겨 생성 요청이 다시 오면 같은 여행이 중복될 수 있습니다. PostgreSQL에서 Idempotency-Key를 먼저 확보하고, 같은 키·같은 내용은 기존 결과를 반환합니다. 내용이 다르면 409를 반환합니다. 8개 동시 요청은 메모리 저장소 테스트로, 실제 DB 고유 제약은 PostgreSQL 통합 테스트로 따로 확인했습니다.

동시에 수정한 일정이 덮이지 않도록

일정 수정 요청에는 기준 버전(baseVersion)을 함께 받습니다. 중복 버전 INSERT는 ON CONFLICT DO NOTHING의 처리 행 수로 판별하고, 최신 버전은 기준 버전과 일치할 때만 조건부 UPDATE합니다. 그사이 다른 편집이 반영됐다면 409를 반환합니다. 초기 SAVEPOINT 방식은 프로젝트 기록상 PostgreSQL 통합 테스트에서 중첩 트랜잭션 예외가 발생해 현재 방식으로 교체했습니다.

성공 응답 뒤에도 이벤트 기록이 사라졌습니다

이벤트 API가 DB 대신 메모리 저장소를 사용해 재시작하면 기록이 없어졌습니다. 호출되는 저장소 구현을 추적해 PostgreSQL Outbox 저장 경로로 연결했습니다. 공개된 main의 발행자는 NoOp이므로 Kafka 발행까지 구현했다고 적지 않습니다.

앱 화면과 추천 기능은 팀원들이 함께 개발했습니다. 위 문제 해결 사례는 제가 맡은 서버 구현입니다.

영상 분석 서비스 · 2인 팀

빈자리 BINJARI

주차장 영상에서 빈자리를 찾아 앱에 알려주는 서비스

서비스

캠퍼스에서 주차장을 돌아다니며 빈자리를 찾는 시간을 줄이기 위한 서비스입니다. 주차장 영상을 분석해 주차면별 점유 상태를 앱에 보여주고, 현재 빈자리 수와 시간대별 혼잡도를 확인할 수 있게 했습니다.

  • 지도에서 주차장 선택 → 전체·점유·빈 주차면 수 확인
  • 주차면별 상태와 관측 기록 기반 시간대별 통계 확인
담당
Flask 분석 서버, 주차면 매핑·상태 API, SQLite 통계
기술
Python, Flask, YOLOv8x, SQLite, Flutter

추론 대상 프레임을 약 80% 줄였습니다

상태가 거의 같은 연속 프레임마다 모델을 실행하지 않도록 5프레임 중 1개만 추론합니다. 추론 대상 프레임 수는 설정상 약 80% 감소하지만, 전체 처리 시간이나 앱 반영 속도가 같은 비율로 개선됐다는 뜻은 아닙니다.

상태 전환에 서로 다른 확인 기준을 둡니다

일반 주차면은 빈자리에서 점유로 바뀔 때 5회, 점유에서 빈자리로 바뀔 때 8회 확인합니다. 한 번의 탐지 누락이 빈자리 안내로 이어질 위험을 줄이기 위한 설계로, 실제 출차 직후에는 반영이 늦어질 수 있습니다.

탐지 박스를 바로 빈자리 수로 세지 않았습니다

차량 탐지 박스가 옆 주차면에 걸칠 수 있어, 주차면 다각형과 박스의 교차 면적을 주차면 면적으로 나눈 뒤 탐지 신뢰도를 곱해 연결 점수를 계산했습니다. 최근 10개 판정과 상태 전이 기준을 거쳐 확정한 결과만 SQLite에 저장하고 앱에 전달합니다.

두 주차장, 56개 주차면을 대상으로 구현했습니다. Flutter 화면은 팀 결과물입니다. 관측값만 쓰는 시간대별 통계 보완과 재생 테스트는 프로젝트 이후 개인 작업입니다.
